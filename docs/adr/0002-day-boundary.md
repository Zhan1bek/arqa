# ADR-0002. Граница дня — в часовом поясе водителя

**Статус:** принято

## Контекст

Водитель в Алматы (UTC+5) работает с 00:00 до 05:00 по местному времени, а по UTC это ещё
предыдущий день. Наивная фильтрация `new Date(start).toISOString().slice(0, 10) === date`
отнесёт ночные поездки не к тому дню. Это классическая ошибка, которую ИИ-ассистенты
генерируют по умолчанию.

## Решение

- Часовой пояс водителя задаётся настройкой сервера `DRIVER_TZ` (IANA, по умолчанию `Asia/Almaty`).
- При записи поездки сервер вычисляет `local_date` — дату начала поездки в `DRIVER_TZ` — и
  хранит её отдельным индексируемым столбцом. Выборка дня: `WHERE local_date = ?`.
- Поездка через полночь относится к дню начала, как смена в таксопарке.
- В ответе API время отдаётся со смещением водителя (`2026-10-01T08:10:00+05:00`), поэтому
  клиенту не нужен Intl с часовыми поясами: время показывается как `start.slice(11, 16)`.
- Время всегда приходит со смещением; «голое» `2026-10-01T08:10:00` отвергается как
  неоднозначное.

## Последствия

- Смена `DRIVER_TZ` не пересчитает уже записанные `local_date`. Для одного водителя это
  нормально; для нескольких часовой пояс станет полем водителя.
- Клиент строит время новой поездки из `utcOffset` дня, который отдаёт сервер. Для поясов
  с переходом на летнее время это неточно в день перехода; в Казахстане перехода нет.
